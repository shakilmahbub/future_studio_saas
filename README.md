# Future Studio SaaS

multi-tenant saas backend built with laravel. every tenant gets its own database, separated by domain (`tenant.localhost`). central app handles tenant registration, plans, subscriptions. tenant app handles customers, users, roles and permissions.

## requirements

- docker + docker compose

## setup

```bash
docker compose up -d --build
```

that's it, no manual commands needed. entrypoint installs dependencies, runs migrations, seeds the database. nginx runs on `localhost:8000`.

central admin after seeding: `admin@central.com` / `password123`.

## creating a tenant

login as central admin first. then `POST /api/v1/tenants` with `name`, `admin_name`, `admin_email`, `admin_password`. this creates the tenant db, runs its migrations and seeders, and gives the admin role to the new user automatically.

tenant apis are at `http://{tenant}.localhost:8000/api/v1/...`. on windows, `.localhost` subdomains don't auto resolve, you need a hosts file entry per tenant. or just use `curl --resolve` for testing without touching the hosts file.

## api docs

docs: `https://futurestudiosaas.docs.buildwithfern.com/future-studio/central/test` (generated by scramble from the code).

postman collection is in `postman/future_studio_saas.postman_collection.json`. import it, run the two Auth > Login requests first, everything else uses the token automatically after that.

## database schema

two databases:

- **central** — `tenants`, `domains`, `plans`, `subscriptions`, central `users`. anything shared across all tenants.
- **per-tenant** — one db per tenant. `users`, `customers`, `roles`, `permissions`, and the laratrust pivot tables.

went with a separate database per tenant instead of one shared table with a `tenant_id` column. full isolation this way, no chance of one tenant's query leaking into another's data, and tenant tables don't need a `tenant_id` column at all.

relationships:

- `Tenant hasOne Subscription`, `Subscription belongsTo Plan` (central)
- `User belongsToMany Role`, `Role belongsToMany Permission` (per-tenant)

`Plan` and `Subscription` need to be readable from inside tenant context too, so they override `getConnectionName()` to always point at the central connection no matter which tenant is active.

## caching

redis, tagged per tenant. `stancl/tenancy`'s `CacheTenancyBootstrapper` tags every cache call with `tenant-{id}` automatically while a tenant is active, so two tenants never share a cache key by accident.

cached: `/permissions`, `/dashboard`, `/subscription/usage`. not cached: `/customers`, `/users` — too write-heavy for the read benefit.

invalidation right now is just ttl (30 min). next step is invalidating on write instead of waiting it out — clear dashboard cache when a customer or user is created/deleted, clear subscription-usage cache when a subscription or plan changes.

## database indexing

foreign key columns (`subscriptions.tenant_id`, `subscriptions.plan_id`, `domains.tenant_id`, the pivot table columns) get indexed automatically through `foreign()`/`foreignId()->constrained()`. `customers.email`, `roles.name`, `permissions.name` are `unique()`, also indexed.

eager loading to avoid n+1: `User::with('roles')`, `Tenant::with('domains')`, `Subscription::with(['tenant', 'plan'])`.

known gap: `customers.phone` and "one subscription per tenant" are only enforced by validation, not a db constraint. two requests at the same time could both slip through. would add a db-level unique index for this before going to production.

## key decisions

- **multi-tenancy** — `stancl/tenancy`, db per tenant. domain resolved via `Host` header, `InitializeTenancyByDomain` middleware.
- **auth** — one jwt guard, not separate central/tenant guards. custom `ctx` and `tenant_id` claims instead. same signing secret either way, so the guard split alone wouldn't stop a central token from working on a tenant route — the claim check in `VerifyTokenContext` middleware is what actually blocks it.
- **rbac** — permissions are a fixed seeded list, tied to real checks in code. roles are dynamic, tenant admins create their own and pick permissions from the list. permissions aren't user-creatable on purpose, a made-up permission name nothing checks for would do nothing.
- **service layer** — used where there's actual multi-step work with a real way to fail (`TenantService`: create tenant, create domain, switch db, create admin user, assign role, all in a transaction). skipped for plain crud like `PlanController` — wrapping one line of `Model::create()` in a service is just extra indirection for nothing.
